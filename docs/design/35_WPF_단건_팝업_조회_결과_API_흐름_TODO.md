## 1. 확정된 API 구성

| 순서 | API | 책임 |
|---|---|---|
| 1 | 로그인 | SSO 사용자 정보를 인증하고 토큰 발급 |
| 2 | 팝업 조회 | 현재 표시 조건을 만족하는 팝업 최대 1건 조회 |
| 3 | 결과 수신 | 현재 표시한 팝업 결과 1건 저장 |

정상 흐름은 로그인 → 조회 → 표시/사용자 처리 → 결과 수신 → 조회다. 토큰 만료 시 로그인한 뒤 실패한 API를 재호출한다. 결과 수신이 만료로 실패했다면 조회부터 다시 시작하지 말고 해당 결과를 보존해 결과 수신을 재시도한다.

## 2. 조회 API 응답

- [ ] 조회는 배열이 아닌 단일 팝업 객체 또는 null을 반환한다.
- [ ] pollingIntervalSeconds를 매 조회 응답마다 반환한다. 첫 조회, 결과 수신 후 조회, 빈 결과 후 재조회에 적용하고 클라이언트는 최신 값을 반영한다.
- [ ] 조회 응답에서 nextStatus를 제거한다. 성공 응답의 단일 nextPopup 값으로 구분한다. 객체이면 표시하고 null이면 폴링 간격 후 다시 조회한다.
- [ ] 조회 오류는 정상적인 null과 구분하여 HTTP/API 오류로 처리한다.
- [ ] 인증 토큰이 사용자 식별을 제공한다면 조회 요청·응답에서 불필요한 userId를 전달하지 않는다. 로그인 요청에 필요한 SSO 식별 값과 인증 이후 조회 계약을 혼동하지 않는다.
- [ ] C# 조회 DTO는 List<PopupDto>가 아닌 단일 PopupDto? 속성으로 정의한다. 질문, 선택지 등 팝업 내부의 반복 데이터만 목록으로 유지한다.
- [ ] 기존 공통·유형별 팝업 필드를 nextPopup 한 개 구조에 매핑하고 JSON 예시, Excel 정의서, Markdown 및 Word 정의서를 함께 갱신한다.

응답 예시: { "pollingIntervalSeconds": 1800, "nextPopup": null }

## 3. 결과 수신 응답의 다음 대상 상태

- [ ] 결과 저장 상태와 다음 대상 상태를 별도로 표현한다. 기존 결과 처리 status는 저장·처리 상태이며, nextStatus는 후속 팝업 후보 유무다.
- [ ] 결과 저장 후 현재 게시·기간·대상·완료 조건에 맞는 후보 건수를 확인하고, 0건이면 nextStatus=EMPTY, 1건 이상이면 nextStatus=AVAILABLE을 반환한다. 실제 쿼리는 COUNT 집계가 필요한지 존재 확인 방식과 비교한다.
- [ ] EMPTY이면 클라이언트는 조회 API를 즉시 호출하지 않고 가장 최근 pollingIntervalSeconds까지 대기한다.
- [ ] AVAILABLE이면 클라이언트가 조회 API를 즉시 호출하여 팝업 단건 객체를 받는다. 결과 수신 응답에 팝업 콘텐츠를 중복해서 포함하지 않는다.
- [ ] 결과 저장은 성공했으나 다음 후보 확인이 실패한 경우를 EMPTY로 오인하지 않도록 오류 계약과 클라이언트 동작을 정한다.
- [ ] 후보 확인과 실제 조회 사이 게시 중단·기간 만료·대상 변경이 있을 수 있으므로, 조회 API는 후보 유효성을 다시 확인하고 null을 정상 처리한다.
- [ ] nextStatus 적용에 따라 결과 응답 DTO·예시·Excel의 RESULT_RESPONSE 및 API 계약 문서를 갱신한다.

응답 예시: { "resultId": "RESULT-001", "status": "SAVED", "nextStatus": "EMPTY" }

status 값과 오류 응답은 기존 RESULT 계약과 맞춰 확정한다. 위 예시 값은 의미 설명용 제안이다.

## 4. 장애 복구 — 세부 결정값 확인 필요

다음 항목은 의사결정 전까지 구현 계약으로 확정하지 않는다.

- [ ] 미전송 결과가 여러 건일 때 단건 순차 재전송 또는 일괄 전송 여부.
- [ ] 미전송 결과가 남아 있을 때 먼저 결과를 처리한 뒤 다음 팝업을 조회할지, 결과를 보관하고 팝업 진행을 허용할지.
- [ ] 결과를 메모리에만 보관할 경우 앱 종료·PC 재부팅 때 유실을 허용할지, 디스크에 영속 보관할지.
- [ ] 결과 저장 성공과 후보 확인 실패를 응답에서 어떻게 구분하고 이후 어떤 API부터 재호출할지.
- [ ] 중복 제출 시 같은 결과로 판정할 식별자·본문 기준과 보존 기간을 기존 resultId·deliveryId 계약에 매핑한다.

일괄 전송을 선택하면 정상 단건 요청과 별도로 배열 요청 및 항목별 처리 결과 계약이 필요하다. 이번 정상 흐름의 단건 응답에 이를 미리 섞지 않는다.

### 2026-10-13 착수 전 확인 — 구현 보류

현행 코드 대조 결과 서버·WPF 모두 목록(popups[])·배치 결과(results[] 최대 50건)·디스크 대기열(pending-results.json) 구조이며 nextPopup·nextStatus·SAVED는 아직 없다. 구현은 아래 결정 전까지 보류한다.

- 확정: 조회 경로는 새 경로를 만들지 않고 기존 `GET /api/wpf/popups` 응답을 단건 구조로 교체한다(구버전 클라이언트 호환 없음, 필요 시 최소 클라이언트 버전 426으로 차단).
- 미결: 결과 수신 요청을 단건으로 바꿀지, 현행 배열을 유지하고 응답에 nextStatus만 더할지(§4 일괄 전송 여부와 연결).
- 미결(신규 확인): **닫기(CLOSED) 후 재노출 기준.** CLOSED는 TEXT·IMAGE의 닫기, 완료 전 닫기를 허용한 설문·퀴즈·영상을 제출·시청 완료 없이 닫은 경우다. 서버는 이를 완료·숨김으로 기록하지 않아(`selectAvailablePopups`는 숨김·완료만 제외) 단건 흐름에서는 결과 수신 직후 nextStatus=AVAILABLE → 같은 팝업 재조회가 반복된다. 현재는 클라이언트가 앱 실행 중 표시한 팝업 ID(`_shownPopupIds`)로 걸러 막고 있다. 서버 기준(당일·폴링 1주기 제외 등) 또는 조회 요청의 제외 목록 중 하나를 정해야 후보 확인(nextStatus)과 조회 기준을 일치시킬 수 있다.

## 5. 서버·클라이언트 정합성 검토

- [ ] 후보 건수 확인은 결과 저장 뒤 실행하고, 저장된 결과를 다시 제출하지 않으면서 다음 대상 상태를 알려준다.
- [ ] 빈 후보면 즉시 별도 조회하는 HTTP 왕복·서버 처리 단계를 줄이는 효과를 측정한다. AVAILABLE은 실제 콘텐츠 조회 API를 호출하므로 후보 확인과 조회가 모두 필요하다.
- [ ] 후보 확인 및 조회가 동일한 사용자·게시·기간·완료·숨김 기준을 사용하도록 확인한다.
- [ ] 동시에 여러 조회가 와도 한 사용자/정책상 진행 단위에서 중복 전달 건이 생성되지 않는지 검토한다.
- [ ] 다중 PC 허용 여부에 따라 진행 단위가 사용자, 장치 또는 세션 중 무엇인지 확정한다.
- [ ] 결과 응답 유실·중복 제출·조회 유실·401 재인증·EMPTY 폴링·AVAILABLE 후 게시중단 시나리오를 계약 테스트로 검증한다.
- [ ] 실제 URL, 토큰 재발급 계약, resultId/deliveryId 사용처, 현재 RESULT_REQUEST 필드, HTTP 및 업무 오류 코드를 기존 서버 구현과 대조한다.

## 6. 완료 기준

- 세 API의 책임과 정상 호출 순서가 서버 계약, C# DTO, Excel/Word/Markdown 정의서 및 샘플 JSON에 일치한다.
- 조회 응답에는 pollingIntervalSeconds와 팝업 단건/null만 있고 userId·nextStatus·팝업 목록이 없다.
- 결과 수신 응답은 저장 처리 status와 후속 후보 nextStatus를 구분한다.
- 회의 미결 항목은 결정 전 임의 구현되지 않고 문서에 보류로 남는다.
- 서버·클라이언트·샘플 테스트에서 정상 단건 흐름과 오류·재시도를 검증한다.
