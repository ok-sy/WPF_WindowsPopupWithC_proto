# 28. TEXT 본문 서식 편집 요구사항 TODO

기준일: 2026-10-08 (KST).
상태: **요구사항 접수 · 개발 여부 결정 보류**.
이 문서는 요구사항과 검토안을 기록한다. 개발 착수, 일정, 최종 API 계약을 확정한 문서가 아니다.

## 1. 요청된 기능

- [ ] TEXT 본문에서 원하는 글자·단어·구간을 선택하여 서식을 변경할 수 있다.
- [ ] 같은 문장 안에서도 구간별로 다른 서식을 사용할 수 있다.
- [ ] 동일한 문자열이 여러 번 있어도 선택한 위치에만 서식을 적용한다.
- [ ] 관리자 화면에서 작성한 내용과 서식을 저장하고 다시 열어 편집할 수 있다.
- [ ] WPF 팝업에서 저장된 내용과 서식을 표시한다.

## 2. 서식 범위 검토안

| 적용 범위 | 후보 기능 | 상태 |
| --- | --- | --- |
| 선택한 글자·구간 | 글자 크기, 색상, 굵게, 기울임, 밑줄 | 개발 결정 시 지원 범위 확정 |
| 선택한 글자·구간 | 글꼴 선택 | 허용 글꼴·배포 방식 검토 필요 |
| 문단 | 왼쪽·가운데·오른쪽 정렬 | 개발 결정 시 확정 |
| 본문 전체 | 기본 글자 크기·기본 서식 | 기존 bodyFontSize와 우선순위 검토 |

자동 줄바꿈으로 생긴 화면상의 한 줄과 Enter로 구분한 문단은 구별한다.
글자 서식은 줄바꿈 이후에도 해당 글자에 유지하고, 정렬은 문단에 적용하는 방향이다.
우선 적용 후보는 TEXT의 일반 본문(plainText 영역)이다.
제목·설명·강조문·하단 설명, 다른 팝업 유형까지 확대할지는 미정이다.

## 3. 데이터 구조 검토안 — Run 및 선택적 문단 구조

문단 구조는 필수가 아니다. 글자 서식과 본문 전체 정렬만 필요하면 본문 전체에 Run 배열 하나를 두고 줄바꿈을 `\n`으로 저장할 수 있다.
문단별 정렬·간격이 필요하면 문단 배열 안에 Run을 두는 구조를 선택한다. 두 형식을 모두 지원한다는 뜻이 아니며, 지원 범위를 정한 뒤 한 가지 기준 구조를 확정한다.
서식 변경이 없으면 단일 배열 방식은 본문 전체에 기본 Run 하나, 문단 방식은 각 문단에 기본 Run 하나를 사용한다. 자동 줄바꿈은 저장된 문단을 추가하지 않는다.


본문 전체를 문단 배열로 저장하고, 문단 안에는 같은 서식의 연속된 글자 묶음(Run)을 순서대로 저장하는 방안을 검토한다.
서식이 있는 글자뿐 아니라 일반 글자와 공백도 모두 포함한다.
Run의 text를 순서대로 연결한 결과가 문단의 본문이며, Run 경계에서 공백이나 줄바꿈을 자동 추가하지 않는다.
동일한 text 값은 고유 식별자가 아니다. 편집기의 선택 위치로 구간을 구분한다.

아래는 구조 설명용 예시이며 필드명·단위·기본값은 최종 계약이 아니다.

```json
{
  "content": {
    "textBlocks": [
      {
        "alignment": "LEFT",
        "runs": [
          { "text": "확인 후 다시 " },
          { "text": "확인", "bold": true },
          { "text": "하세요" }
        ]
      }
    ]
  }
}
```

위 예시는 두 번째 '확인'에만 굵게를 적용한다.
편집기는 선택 범위에 따라 Run을 분할하고, 인접한 Run의 유효 서식이 같으면 합치는 방식으로 정리할 수 있다.
문단 나누기·문단 내부 줄바꿈·빈 문단·연속 공백의 저장 규칙은 별도 확정한다.

- [ ] textBlocks를 새 본문의 기준 데이터로 삼는 방향 검토.
- [ ] plainText와 서식 본문을 독립적으로 수정하여 서로 어긋나는 구조 방지.
- [ ] 일반 문자열이 필요하면 Run과 문단 구분을 반영하여 파생 생성하는 방향 검토.
- [ ] 기존 plainText 데이터의 표시·편집 전환, 구버전 클라이언트 호환 정책 결정.
- [ ] 서식 우선순위는 구간 서식 → 본문 기본 서식 → 앱 기본값 방향으로 검토.
- [ ] 글자 크기 단위·허용 범위, 색상 형식, 글꼴 목록, 최대 글자·문단·Run 수 결정.

## 4. 글꼴 정책 검토

폰트 이름만 전달하면 사용자 PC에 설치된 해당 글꼴을 사용하는 방향이다.
관리자 PC의 TTF/OTF 파일이 JSON을 통해 사용자 PC로 자동 전달되는 것은 아니다.
해당 글꼴이 없으면 대체 글꼴로 표시될 수 있어 줄바꿈과 본문 높이가 달라질 수 있다.

- [ ] 회사 PC 공통 글꼴만 선택지로 제공할지 결정.
- [ ] 글꼴 누락 시 대체 순서 및 기본 글꼴 결정.
- [ ] 일관된 표시가 필요하면 앱에 글꼴 포함 여부와 재배포 라이선스 확인.
- [ ] 관리자 미리보기와 WPF의 렌더링 차이를 허용할 범위 결정.

## 7. SURVEY·QUIZ 확장 검토

개발 여부는 보류하며, 공통 구조로 설계하고 첫 적용을 TEXT로 제한하는 것을 권장안으로 기록한다. SURVEY·QUIZ 동시 구현을 확정하지 않는다.

- [ ] 서식 데이터 모델·검증·관리자 편집기·WPF 렌더링을 유형별로 재사용할 수 있도록 공통화 범위 검토.
- [ ] SURVEY·QUIZ 안내문, 질문, 선택지, 해설을 확장 후보로 기록하고 실제 적용 필드를 결정. 해설 등 기존 미지원 영역의 신규 기능 개발은 별도 판단.
- [ ] 질문·선택지 ID, 응답 값, 정답·점수·채점 규칙은 표시 서식과 분리하여 유지.
- [ ] 유형별 DTO·서버 저장/조회·관리자 질문/선택지 입력·WPF 표시부의 변경 범위 조사.
- [ ] 기존 일반 문자열 데이터의 호환 및 저장 후 재편집 정책 결정.
- [ ] 큰 글씨·혼합 서식·여러 줄 선택지에서도 행 높이, 체크 표시, 클릭 영역, 스크롤이 정상인지 검증.
- [ ] 단일/복수 선택, 필수 입력, 채점, 제출 및 VIDEO+QUIZ 동작 회귀 확인.

## 8. 관리자 등록 화면 우클릭 서식 메뉴

선택한 글자에서 우클릭하면 간단한 색상 팔레트와 글꼴 설정 메뉴를 표시하는 요구사항을 기록한다.
기능 발견성과 키보드 접근을 위해 입력란의 작은 '서식' 버튼으로도 같은 메뉴를 여는 방식을 권장한다.

- [ ] 메뉴 후보: 기본 색상 팔레트·색상 초기화, 글꼴, 크기, 굵게·기울임·밑줄, 서식 지우기.
- [ ] 글자 선택 후 메뉴를 열면 해당 선택 구간에만 적용.
- [ ] 선택 없이 메뉴를 열면 커서 이후 새로 입력할 글자에 적용하는 동작 검토. 기존 본문 전체에 자동 적용하지 않음.
- [ ] 우클릭 및 메뉴 항목 클릭 시 선택 범위·커서 위치를 보존하고 서식 적용 후 편집 위치 복귀.
- [ ] 여러 서식이 섞인 구간을 선택했을 때 메뉴의 혼합 상태 표시 정의.
- [ ] 서식 지우기는 선택 구간의 서식을 기본값으로 되돌리며 글자 내용은 보존.
- [ ] 서식 편집 영역 안에서만 사용자 정의 우클릭 메뉴를 적용하고 바깥은 브라우저 기본 메뉴 유지.
- [ ] 복사·잘라내기·붙여넣기 접근 방법과 기본 단축키를 유지. 사용자 정의 메뉴와 기본 메뉴의 충돌 처리 검토.
- [ ] '서식' 버튼 및 키보드로 메뉴 열기·이동·적용·닫기 지원, Esc로 취소 시 선택 범위 유지.
- [ ] 화면 경계에서 메뉴 잘림 방지, 바깥 클릭 시 닫기, 한글 조합 입력 및 실행 취소·다시 실행 검증.
- [ ] TEXT·SURVEY·QUIZ에서 동일 편집기를 재사용하되 실제 노출 범위는 개발 결정 후 확정.

## 9. 현재 완료 범위

요구사항과 설계 후보를 문서로 기록한 상태이다.
제품 코드·서버 계약·기능 정의서 변경, 의존성 추가, 개발·빌드·실행 검증은 수행하지 않았다.
개발 여부와 세부 지원 범위는 보류한다.
