## 1. 요구사항과 1차 범위

요구: 관리자 화면에서 본문 일부를 선택해 서식(글꼴·색상·크기 등)을 바꾸고 WPF 팝업에 반영한다.

| 대상 | 1차 | 비고 |
| --- | --- | --- |
| TEXT 일반 본문(plainText 영역) | **적용** | 저장→재편집→WPF 표시 왕복을 먼저 검증 |
| TEXT 제목·설명·강조문·하단 설명 | 미적용 | 1차 결과 후 판단 |
| SURVEY·QUIZ 설명 | 미적용 | 공통 구조만 준비(§10) |
| SURVEY·QUIZ 문항·선택지 | 미적용 | DB 변경·레이아웃 검증 필요(§10) |

1차 기능:

- [ ] TEXT 본문에서 원하는 글자·단어·구간을 선택하여 서식을 변경할 수 있다. (구현, 관리자 화면 수동 확인 필요)

## 2. 방식 비교와 결정

| 방식 | 판단 |
| --- | --- |
| 편집기 HTML을 그대로 저장·전달 | 미채택. 편집기 형식이 팝업 전체 계약이 되고, 웹 표시·WPF 파싱·서버 정리 중 한 곳만 어긋나도 위험이 생긴다 |
| 문단·Run JSON 저장, 편집기는 기존 CKEditor 사용 | **채택 방향**. HTML은 편집기 입출력 경계에서만 다룬다 |
| Markdown | 미채택. 색·크기·글꼴을 표현할 수 없고 TEXT에서 제거한 기능 |
| XAML·RTF 문자열 | 미채택. 웹 편집·미리보기 불가, 문자열 로드 위험 |
| 미리 정한 강조 스타일만 제공 | 미채택. 요구(글꼴·색상·구간별 변경)를 줄이는 선택이므로 허용 값 안에서 직접 선택하게 한다 |

채택 방향에서도 변환 작업은 줄지 않는다. 필요한 변환은 다음과 같고, 장점은 HTML을 다루는 위치를 편집기 경계로 모으는 데 있다.

| 변환 | 위치(후보) |
| --- | --- |
| 편집기 HTML → 문단·Run JSON (허용 서식만 추출) | 서버(저장 시) 또는 관리자 웹. 서버는 클라이언트 입력을 신뢰하지 않고 Run JSON 값을 다시 검증 |
| 문단·Run JSON → 편집기 HTML (재편집) | 관리자 웹 또는 서버. text는 반드시 이스케이프 |
| 문단·Run JSON → WPF Inlines | WPF |
| 문단·Run JSON → 관리자 미리보기 | 관리자 웹. React 요소로 생성하고 innerHTML을 쓰지 않음 |
| 문단·Run JSON → 일반 문자열(plainText) | 서버(저장 시 파생) |

## 3. 서식 범위

| 적용 범위 | 기능 | 비고 |
| --- | --- | --- |
| 선택 구간 | 굵게, 기울임, 밑줄 | |
| 선택 구간 | 글자 색 | 대문자 #RRGGBB 형식만 검사. 팔레트·명도 대비로 제한하지 않음(2026-10-09 결정: 형식 검사는 보안 목적, 가독성은 작성자 판단, 색 추가 시 코드 수정 불필요) |

| 선택 구간 | 글꼴 | 기본 글꼴 우선, 필요하면 공통 글꼴 몇 개(§5) |
| 문단 | 왼쪽·가운데·오른쪽 정렬 | |

자동 줄바꿈으로 생긴 화면상의 한 줄과 Enter로 구분한 문단은 구별한다.
글자 서식은 줄바꿈 이후에도 해당 글자에 유지하고, 정렬은 문단에 적용한다.

## 4. 데이터 구조 — 문단·Run JSON

본문을 문단 배열로 저장하고, 문단 안에는 같은 서식의 연속된 글자 묶음(Run)을 순서대로 저장한다.
서식이 있는 글자뿐 아니라 일반 글자와 공백도 모두 포함한다.
Run의 text를 순서대로 연결한 결과가 문단의 본문이며, Run 경계에서 공백이나 줄바꿈을 자동 추가하지 않는다.
동일한 text 값은 고유 식별자가 아니다. 편집기의 선택 위치로 구간을 구분한다.

아래는 구조 설명용 예시이며 필드명·단위·기본값은 최종 계약이 아니다.

```json
{
  "content": {
    "plainText": "확인 후 다시 확인하세요",
    "textBlocks": [
      {
        "alignment": "LEFT",
        "runs": [
          { "text": "확인 후 다시 " },
          { "text": "확인", "bold": true, "color": "#DC2626" },
          { "text": "하세요" }
        ]
      }
    ]
  }
}
```

- 저장 위치: textBlocks는 기존 `POPUP_CONTENT.CONTENT_OPTIONS`(CLOB JSON)에 둔다. 1차 범위는 **DB 컬럼 변경이 없다**.
- 기준 데이터: textBlocks가 있으면 그것이 기준이다. plainText는 서버가 저장 시 textBlocks에서 파생해 기존 `CONTENT_BODY`(CLOB)에 저장하며 관리자가 따로 수정하지 않는다.
- 호환: textBlocks가 없는 기존 데이터·구버전 응답은 지금처럼 plainText로 표시한다.
- 편집기는 선택 범위에 따라 Run을 분할하고, 인접한 Run의 유효 서식이 같으면 합친다.

- [x] 문단 나누기·문단 내부 줄바꿈·빈 문단·연속 공백의 저장 규칙 확정.
- [x] 서식 우선순위: 구간 서식 → 본문 기본 서식(bodyFontSize) → 앱 기본값.
- [x] 글자 크기 단위·허용 목록, 색상 팔레트, 글꼴 목록, 최대 글자·문단·Run 수 결정.
- [x] 허용되지 않은 값의 처리(저장 거부 / 기본값 대체) 결정.

## 6. 편집기 — 기존 CKEditor 재사용 검토

확인 결과(2026-10-09, zero-rule-web):

- 관리자 웹이 사용하는 빌드는 `@cp949/ckeditor5-custom-build` 0.0.15이며, 내장 CKEditor 5 본체는 **v34.1.0**(온라인 빌더 생성)이다. `node_modules/@ckeditor/*` v48.4.0 패키지는 이 편집기가 사용하는 본체가 아니다.
- 포함 플러그인: FontColor·FontSize·FontFamily·Alignment·Underline·Italic·RemoveFormat·Highlight. 필요한 서식 기능이 모두 있다.
- General HTML Support 플러그인은 없다. 임의 HTML을 통과시키는 경로가 없다.
- 빌드에 licenseKey 처리가 없다(v44 이전). v44 이상으로 올리면 GPL 사용 시에도 `licenseKey: 'GPL'` 설정이 필요하다.
- 기존 사용처: `CommonCKEditor`·`BbsCKEditor`(PdsEdit).

- [ ] 라이선스: GPL로 사용하는 것으로 본다. 관리자 웹을 외부(고객사)에 배포·반입하는 형태라면 GPL 배포 의무(소스 제공 등) 해당 여부를 담당 부서에서 확인한다. 기존 PdsEdit 사용 정리 방식을 따른다.
- [ ] v34.1.0 이후 CKEditor 5 보안 권고 해당 여부 확인. — 2026-11-03 대조: 대체: CKEditor5 49.0.1 전환(20261029 CKEditor5 전체 통합)
- [x] 공용 CommonCKEditor 설정은 바꾸지 않고, 팝업 전용 편집 컴포넌트에서 툴바·팔레트·크기·글꼴을 허용 목록으로 제한한다.
- [x] 편집기 HTML의 style 값(색·크기·글꼴)을 허용 값으로 변환·검증하는 코드 작성. 태그 허용 목록(jsoup Safelist 등)만으로는 style 내부 값 검증이 되지 않는다.

## 7. 보안

- 관리자 웹은 저장 데이터를 innerHTML(dangerouslySetInnerHTML)로 표시하지 않는다. Run JSON을 React 요소로 만든다.
- Run JSON → 편집기 HTML 생성 시 text를 반드시 이스케이프한다. JSON 저장이라도 이 단계에서 이스케이프를 빠뜨리면 저장형 XSS가 된다.
- 서버는 관리자 UI를 거치지 않은 API 입력도 같은 규칙으로 검증한다(허용 키·서식 값·길이).
- WPF는 Run JSON 값을 Inline 속성으로 변환하며 HTML/XAML 문자열을 로드하지 않는다. (당시 "허용 목록 값만 변환"은 설계 48에서 서버 정책 검증 + WPF 표시 방어(안전 범위·변환 실패 기본값)로 대체.)
- 일반 조회·표시 경로에서 HTML을 다루지 않으므로 HTML 처리 범위가 편집기 경계로 줄어든다. HTML 위험이 사라진다는 뜻은 아니다.

## 9. 개발 결정 전 왕복 검증 (우선)

작은 본문 하나로 작성 → 저장 → 다시 편집 → WPF 표시를 왕복시켜 실제 구현 부담을 확인한다.

### 9.1 수행 방법 (2026-10-09, 저장소 밖 임시 코드)

- 관리자 웹이 쓰는 실제 빌드(`@cp949/ckeditor5-custom-build` 0.0.15, CKEditor 5 v34.1.0)를 WebView2 페이지에 올리고 허용 목록(색 4종, 크기 12·14·16·20·24px, 글꼴 2종, 정렬 3종)으로 설정.
- 편집 모델로 본문을 만들고 색·크기·글꼴은 사용자가 구간 선택 후 누르는 것과 같은 편집기 명령(`fontColor`·`fontSize`·`fontFamily`)으로 적용.
- `getData()` HTML → Run JSON 변환 → Run JSON → HTML 생성 → `setData()` → `getData()` → Run JSON 재변환 후 비교.
- Run JSON을 WPF `TextBlock` Inlines(문단별 TextAlignment, `
`→LineBreak)로 렌더링해 이미지로 확인.
- 변환기는 검증용 JavaScript로 작성했다. 운영 구현 위치(서버/관리자 웹)는 §2 기준으로 별도 결정한다.

### 9.2 결과

- [x] Run JSON 왕복 일치: 한글, 앞뒤·연속 공백, 빈 문단, 문단 내부 줄바꿈(Shift+Enter→`<br>`), 정렬, 굵게·기울임·밑줄, 색·크기·글꼴 혼합 구간, `<script>`·`&`·따옴표 문자열이 재편집 후 동일한 Run JSON으로 돌아왔다.
- [x] WPF 표시: 색·크기·글꼴·굵게·기울임·밑줄·정렬·줄바꿈·공백이 의도대로 표시되고 `<script>` 문자열은 글자 그대로 표시되었다.
- [x] 비허용 입력: 정렬 justify, 팔레트 밖 색(hsl), 18px, 비허용 글꼴, `img`·`a`·`script`, 제목 태그를 넣은 HTML에서 허용 서식만 남았다.
- [x] HTML 문자열은 왕복 후 같지 않았다(`&nbsp;` 위치, 태그 중첩 순서, `"` 이스케이프). 의미는 같으므로 **비교·저장 기준은 Run JSON이어야 하며 HTML을 저장하지 않는 결정이 맞다**.

### 9.3 확인된 규칙·주의점 (개발 시 반영)

- [x] 빈 문단은 편집기에서 `<p>&nbsp;</p>`로 나온다. 공백 하나뿐인 문단과 구분되지 않으므로 "공백 하나뿐인 문단 = 빈 문단"으로 정한다. WPF는 빈 문단에도 한 줄 높이를 유지해야 한다.
- [x] `&nbsp;`는 일반 공백으로 저장한다. 재편집 HTML 생성 시 앞뒤·연속 공백은 `&nbsp;`로 되돌려야 접히지 않는다.

### 목표

폐쇄망의 **CSS 별칭 하나에 굵기별 `@font-face`와 `src: local(...)`를 연결하는 구조**를 로컬 Windows에 재현한다. CKEditor에서 선택한 글꼴과 굵기가 인라인 미리보기, 실제 크기 미리보기, 저장 후 재편집, WPF Agent에 동일하게 표시되도록 구현하고 회귀 검증한다. 일치 기준은 선택된 패밀리·서체·굵기와 기존 글자 서식의 보존이다. 브라우저와 WPF의 픽셀 단위 렌더링 비교는 합격 기준에서 제외한다.

### 로컬 검증 구성

| 구성 | CSS 선언 | 확인 목적 |
|---|---|---|
| 같은 패밀리 | 별칭 하나에 400·700을 등록하고 Windows에서 같은 패밀리로 확인된 Regular·Bold를 연결 | 기존 `font`와 `bold`로 세 화면이 같은 서체를 선택하는지 확인 |

- 예시 `@font-face`는 개발 가이드나 기존 테스트 화면에 한정해 로드한다. 등록은 에디터가 처음 마운트되기 전에 한 번 수행하고 기존 등록 항목을 같은 목록에 포함한다.

### 구현 전에 결정할 사항

정책을 다시 정할 항목은 없다. 실측에서 일반체와 굵은체가 같은 Windows 패밀리로 확인되면 기존 계약으로 진행한다.

**굵기별 Windows 패밀리가 다르고 기존 계약만으로 왕복 복원이 불가능할 때만 전달 표현을 결정한다.**

- 이유 · WPF가 표시할 실제 패밀리와 CKEditor가 다시 열 때 복원할 글꼴 선택·Bold 상태를 함께 보존해야 한다. 별칭과 패밀리의 역매핑이 모호하거나 Bold 전용 패밀리에서 굵기가 두 번 적용될 수 있다.
- 선택지 · A. 기존 `font`·`bold` 유지. 굵기별 패밀리의 왕복 매핑이 유일하며 WPF 중복 굵기를 피할 수 있는 경우에 적용. B. 편집 상태와 WPF 렌더링에 필요한 정보가 기존 두 값으로 표현되지 않을 때만 계약 확장 검토.
- 추천 · A의 왕복 가능성을 먼저 검증한다. 저장본의 Bold 상태를 임의로 제거해 재편집 상태를 잃지 않도록 한다.
- 영향 · B가 필요하면 웹 직렬화·역변환, 서버 검증·보존, API 문서, 구버전 WPF의 처리와 배포 순서를 함께 검토한다. 200·300이나 500·700을 개별 선택·복원해야 한다는 요구가 확정될 경우에만 숫자 굵기 필드를 검토한다.

### 현상과 목표

폐쇄망 `main/styles/globalStyle.ts`의 `em, i { font-style: normal; }` 규칙이 CKEditor 본문의 기울임 표시를 덮는 현상이 보고됐다. 캡처의 `//`는 CSS 템플릿 문자열에서 CSS 주석으로 해석되지 않는다. 재현 시 DevTools에서 영향을 받는 요소와 적용된 규칙을 확인한다.

선택 영역에 기울임을 켜고 끄면 편집기에서 즉시 표시되고, 웹 미리보기·저장 후 재편집·WPF에도 같은 서식이 적용되어야 한다. 굵게와 함께 적용하거나 커스텀 글꼴을 선택해도 해당 글꼴과 두 서식이 보존되어야 한다.

### 구현 시 확인할 사항

| 위치 | 확인 및 변경 범위 |

| 폐쇄망 `main/styles/globalStyle.ts` | Elements에서 `<em>`·`<i>`의 Computed `font-style`과 최종 적용 규칙을 확인한다. 전역 리셋의 영향이 확인되면 공통 CKEditor의 편집 본문에만 스타일을 보완한다. |
