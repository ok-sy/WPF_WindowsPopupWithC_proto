## 1. 확정한 흐름

인증 헤더 → 기존 인증 처리에서 currentId(사번) 획득 → Controller → Service → DTIY3121 대상자와 DTIY3117 게시내용 JOIN → 전체 JSON 파싱·검증 → WPF 응답.

- [ ] currentId가 내부 숫자형 사용자 ID가 아닌 DTIY3121.ENO에 대응하는 사번인지 확인한다.
- [ ] Controller의 조회 메서드에서 요청마다 currentId를 얻는다. 사용자 정보를 private/final 필드 초기화식에서 읽거나 공유 Controller 필드에 보관하지 않는다.
- [ ] 조회에 필요한 입력이 사번뿐이면 RequestBody 및 popupId RequestParam을 제거한다. API Demo는 본문 생략 또는 빈 객체 `{}`로 호출한다.
- [ ] 기존 인증 처리를 그대로 사용하고 중복되는 UserResolver의 Bean·필드·생성자 인자·호출만 제거한다. 인증 필터·토큰 검증을 제거하거나 클라이언트 본문의 사번을 신뢰하는 방식으로 대체하지 않는다.

## 2. Mapper · XML · 조회 VO

사진 기준 DTIY3121 주요 컬럼: ENO(VARCHAR2 6), POPU_ID(VARCHAR2 10), OBJ_REG_DTTM(VARCHAR2 14). 사진의 복합 PK는 세 컬럼이다. 확정 DDL·외래키·업무 조건은 별도 확인한다.

- [ ] 신규 3117 Mapper 메서드를 `PopupBulletinRow selectByEmployeeNo(@Param("employeeNo") String employeeNo)` 형태로 변경한다. XML은 `#{employeeNo}`를 사용한다.
- [ ] DTIY3121 T와 DTIY3117 C를 `T.POPU_ID = C.POPU_ID`로 JOIN하고 `T.ENO = #{employeeNo}`로 조회한다.
- [ ] 출력은 `C.POPU_ID AS popupId`, `C.POPU_BLTN_CN AS popupJson`을 유지한다. 조회 VO는 popupId(String), popupJson(String) 구조를 보존한다.
- [ ] resultMap은 SQL 결과 컬럼/별칭을 VO 속성에 대응시킨다. 조인 테이블 수와 무관하며, CLOB 내부 JSON은 MyBatis가 아닌 Service의 ObjectMapper가 파싱한다.
- [ ] 명시적 resultMap의 CLOB 매핑은 String/ClobTypeHandler 등 기존 환경의 정상 설정에 맞춘다. resultType과 resultMap을 동일 select에 중복 지정하지 않는다.
- [ ] 같은 사번의 다수 대상 행을 단건으로 선택하는 기준을 확정한다. `OBJ_REG_DTTM DESC, POPU_ID DESC`는 테스트용 최근 등록 순서일 뿐 실제 우선순위가 아니다. 단건 메서드에 여러 행을 반환하지 않는다.
- [ ] 완료·나중에 보기·게시 기간·재노출 조건은 담당 규칙을 확인한다. 무조건 최신 한 건만 선택해서 동일 팝업이 계속 노출되는 것을 완료된 후보 선정으로 간주하지 않는다.
- [ ] FETCH FIRST 지원 여부를 현장 Oracle 버전과 대조한다. Mapper XML 테스트는 실행 필수 Bean이 아니지만 삭제하지 않고 입력 바인딩·출력 매핑 변경에 맞춰 갱신한다. 실제 Oracle 조인 성공은 별도 검증한다.

## 3. Service · Bean 최소화

기준 파일: `zero-rule-server/service/core/src/main/java/server/service/core/popup/sample/fulljson/PopupFullJsonSampleService.java`.

- [ ] Service에 @Service를 적용하고 Mapper·ObjectMapper만 생성자로 주입한다. Controller에서도 ObjectMapper가 필요하면 생성자에 주입한다. 선언만 한 미초기화 필드를 사용하지 않는다.
- [ ] 기존 Config의 Defaults Bean 및 Service Bean 등록을 제거한다. 다른 유효 Bean이 없을 때만 Config 클래스를 제거하며 @Service와 @Bean을 중복 등록하지 않는다.
- [ ] @ConditionalOnProperty는 값 검증이 아니라 Bean 등록 조건이다. 조건 없이 사용할 신규 Service/Controller라면 해당 조건을 정리한다. 다른 샘플 활성화 설정까지 일괄 제거하지 않는다.
- [ ] 조회용 Defaults 필드·생성자 인자·fill/applyDefaults 호출·미사용 설정파일 로딩을 제거한다.
- [ ] 기존 PopupFullJsonDefaults는 기본값 외에도 Rule·ENUM·타입·범위 검증 및 오류 생성에 참조된다. 파일을 삭제하기 전에 검증 책임을 Service 또는 별도 검증 클래스로 옮긴다. 기본값 보정 제거와 검증 제거를 혼동하지 않는다.
- [ ] `nextPopup(String employeeNo)`에서 Mapper 조회 → CLOB 객체 파싱 → 필수값 검증 → SURVEY 정답 키 제거 → 식별자/응답 조립을 수행한다.
- [ ] 샘플 최소 Service 코드에는 전체 옵션 타입·범위 검증이 포함되지 않음을 명시한다. 최소 본문·URL·문항 검증을 전체 계약 검증 완료로 표현하지 않는다.
- [ ] 파싱 실패·객체가 아닌 루트·필수 콘텐츠 부족을 정상 빈 팝업으로 숨기지 않는다. 조회 결과 자체가 없을 때만 popup:null을 반환한다.

## 4. 기본값은 등록 · 수정에서 적용

2026-10-27에 확정한 값은 유지하되 **적용 위치를 등록·수정 단계로 변경**한다. 조회 전용 설정파일/Bean은 불필요하다.

- [ ] 등록·수정에서 공통·유형별 기본값을 채운 전체 popup JSON을 POPU_BLTN_CN에 저장한다. 서버 등록 담당과 적용 책임을 맞춘다.
- [ ] IMAGE·VIDEO의 content.showDescription=false, VIDEO의 allowPlaybackRateChange=false·allowSeek=false를 기본값으로 적용한다. 영상 QUIZ도 동일한 VIDEO 기본값을 따른다.
- [ ] 누락/null에만 적용하고 명시한 true/false·유효한 0을 보존한다. IMAGE 크기 미지정 의미도 유지한다.

## 5. 저장 JSON · 관리자 공통 컴포넌트 경계

- [ ] POPU_BLTN_CN의 루트는 popup 객체 자체다. `{ "popupType": ..., "content": {...}, "questions": [...] }`이며 배열이나 response/popup wrapper로 감싸지 않는다.
- [ ] 문항은 저장 객체 최상위 questions 배열에 포함한다. content 내부의 questions로 옮기지 않는다.
- [ ] Service는 `{ "pollingIntervalSeconds": 1800, "popup": {...} }`를 반환하고 Controller는 그대로 반환한다. Java 변수명 response/pops는 자유지만 JSON 키 popup은 계약대로 유지한다.
- [ ] popupId는 DB POPU_ID 기준, deliveryId는 현재 저장·재사용 없는 테스트 UUID다. 클라이언트 저장 원본의 deliveryId/pollingIntervalSeconds는 신뢰하지 않는다.
- [ ] 공통 컴포넌트가 지원하는 항목의 에디터 → 저장 변환 → 동일값 재조회 → 에디터 복원을 검증한다. 키 순서가 아닌 값과 표시 의미의 보존을 기준으로 한다.
- [ ] 유형별 content 허용 목록·정규화가 있으므로 임의 키의 무손실 왕복은 보장하지 않는다. 저장에서 필드를 빼면 기본값/복원 결과가 달라질 수 있음을 인계한다.
- [ ] 기존 지원 항목 왕복 보장이 제공 범위다. 추가 기능·JSON 확장·서버/CS 추가 대응은 해당 담당 범위로 인계하며 이 TODO에서 자동 구현하지 않는다.
- [ ] 관리자 편집 원본을 WPF용 SURVEY 정답 제거 응답으로 대체하지 않는다. 실제 등록 API 호출 연결과 샘플의 setSaved 요청 표시를 구분한다.

## 6. Orange CLOB 테스트 데이터 입력

- [ ] SQL 리터럴 길이 오류는 CLOB 용량과 별개다. 오류 번호는 ORA-01704인지 원문으로 확인한다(ORA-01074와 다름).

## 7. API Demo 결과 저장 생략 테스트

DB 저장 없이 수신 성공만 흉내 내는 **테스트 전용 결과 endpoint**의 응답:

```json
{
  "resultId": "요청의 resultId 그대로",
  "status": "ACCEPTED",
  "nextStatus": "EMPTY"
}
```

- [ ] HTTP 200과 위 객체를 직접 반환한다. 요청 resultId의 누락·빈 값을 검증하고 다른 ID를 생성하지 않는다. 빈 본문/빈 객체는 정상 종결 응답이 아니다.
- [ ] 이 endpoint는 실제 저장을 하지 않으며 DB 저장 성공의 증거로 사용하지 않는다. 실제 저장 API와 혼동하지 않도록 테스트용임을 표시한다.
- [ ] WPF 결과 URL은 `popup-frameWork/Popup/Services/PopupApiService.cs`의 PostResultAsync에서 확인하고 실제 Java 매핑과 맞춘다. 기준 경로는 `/api/wpf/popups/results`이나 현장 변경 여부를 대조한다.
- [ ] 응답 DTO는 `Popup/Dtos/WpfResultDtos.cs`의 WpfResultResponseDto(resultId/status/nextStatus)다. Java 공통 응답 envelope를 추가해서 DTO 위치를 바꾸지 않는다.
- [ ] 미전송 큐는 `Popup/Services/PopupResultQueue.cs`에서 로컬 파일에 보관한다. 응답 resultId가 요청과 일치하고 ACCEPTED/DUPLICATE/REJECTED인 경우 종결·제거된다. 통신 실패·재시도 오류는 보관된다.
- [ ] ACCEPTED 모의 응답으로 큐 항목이 제거되면 실제 결과가 DB에 남지 않는다. 테스트 데이터만 사용하고 미전송 파일 전체 삭제로 해결하지 않는다.
- [ ] API Demo는 수동 모드다. EMPTY로 대기 의미를 전달해도 버튼으로 재조회할 수 있으며 대상자 SQL의 상태를 갱신하지 않으면 같은 팝업이 다시 조회될 수 있다.
