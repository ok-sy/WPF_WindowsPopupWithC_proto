## 구현 (2026-11-11) — 401·로그인 실패 통합 복구 진입

- **코드 경로 확인:** 로그인 실패는 두 갈래로 올라온다. 연결 오류·5xx·타임아웃은 `SsoAuthHeaderProvider.LoginAsync()`가 그대로 전파해 기존 `IsTransient` 복구로 들어간다. SSO 거절·필수 태그 없음·로그인 API 4xx는 토큰 없이 요청을 보내고, 서버 401 → `OnUnauthorizedAsync` 재로그인 1회 → 다시 401이면 `HttpRequestException(401)`로 올라온다. 따라서 조회 단계의 "1회 재인증 후 401"을 복구 대상으로 넣으면 로그인 실패도 같은 사이클을 탄다.
- **결과 전송 401:** `PopupResultQueue.FlushAsync()`는 400 외 전송 예외를 모두 미종결(Blocked)로 보관하고, `MainWindow`는 Blocked면 조회를 보류하고 `NextDelay()`로 복구 예약한다. 401도 이 경로라 코드 변경 없이 통합 주기가 적용된다(같은 resultId 유지).
- **변경:** `PopupPollingRecovery.IsRecoverable()` 추가(`IsTransient` + HTTP 401). `MainWindow.LoadAndShowAvailablePopupsAsync()`의 조회 예외 분기를 `IsRecoverable`로 바꿨다. 로그인 단계의 실패 전파 기준(`IsTransient`)은 바꾸지 않는다. 400·403·데이터 오류는 정상 조회 간격, 426은 기존 업데이트 안내·종료.
- **중복·무한 재시도 방지:** 별도 타이머를 만들지 않고 기존 일회성 `_pollingTimer` 하나로 다음 요청만 예약한다. 401 재인증은 요청당 1회(`SendWithAuthAsync` retried 플래그) 그대로다. 조회 성공 시 `Reset()`.
- **결과→조회 단계 횟수 분리(같은 날 보완):** 결과 재전송이 저장에 성공하면(`nextStatus`가 EMPTY·AVAILABLE·생략 모두) 결과 단계 복구 성공으로 보고 횟수를 초기화한다. 이어지는 조회가 실패하면 조회 단계 복구를 1회(10초)부터 따로 센다. 이전에는 EMPTY만 초기화하고 AVAILABLE·생략은 조회 성공까지 결과 단계 횟수를 이어 셌다. 저장한 결과가 없는 빈 큐는 조회 복구 횟수를 건드리지 않으며, 미종결 결과가 있으면 조회하지 않으므로 '결과 전송 성공만으로 조회 복구 초기화 금지'와 충돌하지 않는다.
- **검증:** `Popup.csproj` 빌드 경고·오류 0. `Popup.RecoveryTests` 210건(반복 401 응답 예외가 복구 대상, HTTP 상태별 복구 분류, 426·JSON 제외), `Popup.BehaviorTests` 1,730건(실제 `MainWindow` 흐름에서 조회 401 → 10초 복구 예약, 403·400 → 정상 간격, 결과 전송 401 → 조회 보류·10초 복구 예약, 결과 단계 3회 소진 후 AVAILABLE·nextStatus 생략 저장 성공 → 이어진 조회 실패가 1,810초가 아닌 10초), `ApiDemoTests` 124건 통과. 두 검증 프로젝트는 Git 제외 로컬 프로젝트다. 실제 SSO·서버로 401·로그인 실패를 만드는 실환경 실행과 폐쇄망 확인은 미실행.

## 추가 결정·구현 (2026-11-11) — 잘못된 2xx 결과 응답 실행당 3회 상한

- **배경:** 결과 전송에서 HTTP 2xx인데 응답 내용이 잘못된 경우(빈 본문·JSON 오류·응답 resultId 불일치·status 누락/미지원 값)는 미종결로 보관하고 조회를 보류했다. 상한이 없어 서버 응답 오류가 계속되면 그 실행 동안 1시간 주기 재전송만 반복하고 새 팝업을 받지 못한다(복구 무한 루프).
- **즉시 무시안 기각:** 서버가 저장하지 못한 상태에서 바로 무시하면 전달 건이 OPEN으로 남아(POL-10-03) 유예 없이 다음 조회에서 같은 팝업이 다시 내려오고, 닫을 때마다 같은 오류가 나면 사용자 화면에서 같은 팝업이 반복된다. 결과도 유실된다.
- **확정:** 같은 resultId를 실행당 3회(`PopupResultQueue.MaxInvalidResponseAttemptsPerSession`)까지만 재전송한다. 3번째 잘못된 응답에서 이번 실행의 전송 대상에서 빼고(메모리 보관 유지) 그 Flush에서 바로 다음 결과로 넘어가며 조회를 막지 않는다. 일시 오류면 재전송으로, 서버가 이미 저장했다면 DUPLICATE로 정상 종결된다. 상한 도달 시 resultId·deliveryId·popupId와 응답 요지를 로그로 남긴다.
- **상한 미적용:** 응답 없음(타임아웃·연결 끊김)·5xx·401·RETRYABLE_ERROR는 일시 장애라 상한 없이 통합 복구 주기로 계속 재전송한다. HTTP 400 격리·INTERNAL_ERROR 3회 상한(45-3 임시 예외)은 그대로다.
- **남는 위험:** 상한에 걸린 결과가 서버에 저장되지 않았다면 같은 팝업이 다시 내려올 수 있다(서버 응답 오류가 원인이라 클라이언트에서 막을 수 없음). 팝업 조회 응답이 비거나 깨진 경우는 기존대로 복구 대상이 아니며 정상 조회 간격을 기다린다.
- **구현:** `PopupResultQueue`에 resultId별 잘못된 응답 횟수(`_invalidResponseAttempts`)와 `CountInvalidResponse()` 추가. `FlushAsync()`에서 `JsonException`·`InvalidOperationException`(빈 본문)을 이 횟수로 세고, `Settle()`에서 resultId 불일치·응답 null·status 누락/미지원 값을 센다. 종결 시 횟수를 지운다.
- **검증:** `Popup.csproj` 빌드 경고·오류 0. `Popup.RecoveryTests` 231건(유형 6종 각각 3회 재전송·2회 보류 후 3회째 조회 허용·보관 유지·뒤 결과 전송, RETRYABLE_ERROR·503은 5회 모두 재전송, 잘못된 응답 뒤 ACCEPTED 정상 종결), `Popup.BehaviorTests` 1,730건, `ApiDemoTests` 124건 통과. 실제 서버 응답 오류 재현·폐쇄망 확인은 미실행.

- **별도 조회 추적 ID를 추가하지 않는다.** 현재 조회 응답은 requestId를 제공하지 않는다. 확보 가능한 `popup.deliveryId`로 전달 건을 식별하므로 조회 시 requestId 채번·요청 전달·응답 헤더 추가는 이번 범위에서 제외한다.
- `deliveryId`를 확보하면 장애 결과에 포함한다. 식별 가능한 전달 건은 오류 종결로 처리하며 사용자 완료로 기록하지 않는다.
- JSON 파싱 실패 등으로 `popupId`·`deliveryId`를 식별할 수 없으면 null 또는 생략한다. 식별자 미확보만으로 장애 결과 전송을 막지 않으며, 임의의 전달 건을 완료시키지 않는다.
- 결과 자체의 식별자는 WPF에서 생성하고 같은 결과 재전송 시 동일 ID·본문을 유지한다. Git 계약의 `resultId`와 폐쇄망 결과 저장에서 사용하는 `requestId` 명칭을 구분하며, 이번 결정으로 필드를 개명하거나 조회 추적 ID로 혼용하지 않는다.
- **`resultDesc`는 UTF-8 최대 1,000 Byte이며 저장 규격은 `VARCHAR2(1000 BYTE)`다.** 오류 내용과 확보 가능한 JSON 위치 정보를 담고 원본 JSON 전체는 넣지 않는다. 문자 수 1,000자 제한으로 해석하지 않는다.
- 장애 결과의 `resultId`·`resultCode=400`·`resultDesc` 필수, `resultType` null/생략 허용 및 임의 CLOSED 생성 금지라는 확정 정책을 유지한다.

### 구현 시 확인할 사항

- [ ] `popup-frameWork/Popup/Services/PopupApiService.cs`의 `GetNextPopupAsync()`·`SendWithAuthAsync()`, `MainWindow.xaml.cs`의 `LoadAndShowAvailablePopupsAsync()`: 파싱·변환·표시 실패 단계에서 확보한 popupId·deliveryId만 장애 결과 생성 경로에 넘긴다. 조회 추적 ID를 새로 요구하지 않는다.
