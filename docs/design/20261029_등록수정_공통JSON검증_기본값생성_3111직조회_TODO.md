## 확정 설계

- 등록·수정 시 **공통 모듈**이 popup 전체 JSON의 타입·필수값·ENUM·범위를 검증하고, 생략/null에만 기본값을 채워 정규화된 popup JSON을 반환한다. 유효하지 않은 명시값은 임의 보정하지 않고 오류로 반환한다.
- 등록·수정 서비스는 공통 모듈이 성공 반환한 결과만 DB에 저장한다. 검증 실패 시 쓰기/COMMIT 금지.
- 조회는 **저장 시 완성한 JSON을 읽어 그대로 전달**하는 방향이다. DTIY3111 경로에서 `PopupSingleResponseAssembler`를 더 이상 호출하지 않는다. 3117도 조회 시 기본값 생성 책임을 갖지 않는다.
- 조회에 필요한 DB 행 식별, 인증 사번(currentId)·DTIY3121 ENO 조인·대상자 선정, 서버 발급 deliveryId, pollingIntervalSeconds, 응답 envelope, SURVEY 정답 노출 제한 등 **동적·보안 책임은 그대로 유지**한다. 여기서 직조회란 검증·기본값 재조립을 하지 않는다는 뜻이지 DB CLOB을 HTTP 응답 바이트로 무검증 중계한다는 뜻이 아니다.
- 현행 3111 컬럼 기반 매핑 구조가 실제로 전체 popup JSON 직조회가 가능한지 확인하고, 저장 스키마/기존 데이터 이행을 별도 검증한다. 임의로 3111에 CLOB 컬럼이 있다고 가정하지 않는다.
- 기존 3111과 3117 경로를 혼동하지 않고, 이전 샘플은 실제 전환이 끝날 때까지 보존한다.

## 1. 공통 검증·기본값 모듈

- [ ] 입력·출력 계약 확정: 입력 popup JsonNode/문자열 + 검증 정책 버전, 출력 정상화한 popup JSON 또는 구조화 오류(`path`, `code`, `expected`, `actual`, `message`). 원본 입력 변경 금지.
- [ ] 입력이 유효한 JSON 객체인지, 최상위 popupType/content/questions 구조가 올바른지 검사한다. 조회 응답 envelope({pollingIntervalSeconds,popup})와 등록 저장용 popup 본체를 구분한다.
- [ ] 타입별 TEXT / IMAGE / VIDEO / SURVEY / QUIZ와 영상 QUIZ(`popupType=QUIZ`, `content.videoEnabled=true`) 필수 필드·문항·정답·선택지 타입을 검사한다. IMAGE_FILL은 현행 독립 `popupType`이 아니므로 별도 타입으로 만들지 않는다.
- [ ] 공통/유형별 각 필드에 대해 bool/string/number/integer/object/array, ENUM 및 범위를 검사한다. 문자열 `"true"`·`"videoEnabled"`를 boolean으로 자동 변환하지 않는다. 타입 오류를 기본값으로 숨기지 않는다.
- [ ] 선택값이 누락/null인 경우에만 기본값 적용; 명시적 false, 유효한 0, 빈 문자열의 계약상 의미를 유지한다. 필수 콘텐츠/ID를 기본값으로 가리지 않는다. nullable 값은 계약에 따라 별도 처리한다.
- [ ] IMAGE 크기 미지정·ORIGINAL 조건, VIDEO 재생 옵션, QUIZ 영상 상속 및 SUBMIT/LINK_AND_CLOSE 규칙 등 조건부 정책 반영.
- [ ] 3111 Assembler의 기본값과 3117 Defaults/YAML 기본값이 **현재 서로 다른 항목**(예: VIDEO allowSeek·allowPlaybackRateChange, IMAGE showDescription)이 있음을 비교하고 단일 등록 기본값을 명시적으로 확정한다. 암묵적으로 어느 한쪽 값 채택 금지.
- [ ] 경고·기본값 적용 이력(`path`, `before`, `after`, `reason`)을 수집하되 정상 저장 가능 여부는 ERROR 기준으로 결정한다. 관리자/API에는 필드별 문제를 가시적으로 반환하고 운영 토큰·민감값은 로그에 출력하지 않는다.
- [ ] 타입별 규칙 정의와 기본값 표를 중앙 관리하고, 서버와 Demo JSON Validator의 정책 차이를 문서화/대조한다. C#과 Java를 무조건 동일 코드로 공유할 수 있다고 가정하지 않는다.

## 2. 등록·수정 연결

- [ ] 실제 관리자 저장·수정 API → 서비스 → DB 저장 경로를 확인하고 **DB 쓰기 직전** 같은 공통 모듈을 사용한다. 수정 시 부분 PATCH인지 전체 JSON 교체인지 확인해, 부분 업데이트라면 기존 값과 병합한 후 최종 객체 검증·저장.
- [ ] 서버 소유 `popupId`, `deliveryId`, `pollingIntervalSeconds`의 저장 경계를 확정한다. 클라이언트가 지정한 deliveryId 등을 신뢰하거나 저장 JSON에 영속화하지 않는다.
- [ ] 관리자 원본 및 조회 응답의 SURVEY 정답 제거를 구분한다. 원본의 정상적인 편집·재조회 왕복과 WPF 노출 방지 모두 보존한다.
- [ ] 정규화된 결과를 DB에 저장하고 같은 요청 반복 시 결과가 재차 변하지 않는 **멱등성**을 확인한다.

## 3. 조회 전환

- [ ] 사용하지 않는 Assembler/Defaults/Config는 실제 호출 제거와 테스트 대체 후에만 삭제한다. 기존 DTIY3111 샘플의 무관한 계약·코드는 보존한다.
