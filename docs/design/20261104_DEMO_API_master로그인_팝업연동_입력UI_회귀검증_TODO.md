## 목적

SSO 호출 없이 테스트 계정 `master` / 비밀번호 `1111`로 로그인하고, 발급된 인증 정보를 이용해 **팝업 단건 조회 → 팝업 표시 → 결과 단건 전송 → 다음 조회**를 수동으로 회귀검증한다. 동시에 Demo API 입력창의 사용성을 개선한다.

> **중요한 현행 계약 차이:** 기존 WPF 프로토타입 로그인 `POST /api/wpf/auth/login`은 `{lgonId, classCode, linkYn}`을 받는 **SSO 기반 토큰 발급 모의 API**이며 비밀번호를 받지 않는다. 한편 관리자 웹의 `api.auth.signIn({lgonId, passwd})`은 **별도의 일반 로그인 경로**다. 따라서 `master:1111`이 현재 WPF 로그인 API에서 그대로 동작한다고 가정하면 안 된다. 일반 로그인 API의 URL·실제 응답 형식·인증 쿠키/헤더·팝업 API 인증 호환 여부를 먼저 확인한 뒤 연결 방식을 결정한다. 임의로 프로토타입 로그인에 비밀번호를 끼워 넣거나 SSO가 성공한 것처럼 처리하지 않는다.

## 1. 선행 조사 — 실제 인증 계약

- [ ] **A-01** `zero-rule-web/sub/domain/src/user-apis/AuthApi.ts`의 `signIn` 및 `AUTH_API_URL.signIn` 실제 경로·요청/응답을 확인한다. 테스트 계정은 `lgonId=master`, `passwd=1111` (로그·문서에 실제 비밀번호 보존 금지).
- [ ] **A-02** `zero-rule-server` 로그인 구현 및 Spring Security 설정에서 반환이 JSON 최상위 토큰인지, `body` 중첩인지, 응답 헤더/쿠키 기반인지 확인한다. `WpfLoginClient`가 기대하는 `{accessToken,tokenType,expiresAt}`와 대조한다.
- [ ] **A-03** 일반 로그인으로 얻은 인증값이 `POST /api/wpf/popups`와 `POST /api/wpf/popups/results`에서 유효한지 서버 인증 필터 기준으로 확인한다. WPF 프로토타입 토큰과 일반 관리자 세션의 차이 및 환경별 플래그를 기록한다.
- [ ] **A-04** 일반 로그인으로 팝업 API 인증이 불가능하면, **테스트 전용으로 명시적으로 승인된** 연동 방식을 결정한다(운영 인증 우회, 임의 고정 토큰, 사용자 위조 기능을 운영 코드에 추가하지 않음).
- [ ] **A-05** 기존 `DemoWindow.AuthTest.cs`의 SSO·로그인 테스트와 `DemoWindow.Api.cs`의 API Demo 로그인 기능을 구분하고, 이번 회귀검증이 **API Demo**에 속함을 명시한다.

## 2. API Demo 수동 회귀검증 시나리오

- [ ] **R-01 환경/실행**: `Popup.exe -Demo -Api`로 진입, 대상 Base URL 및 로그인 경로 확인. 자동 폴링이 실행되지 않는지 점검.
- [ ] **R-02 SSO 미사용 로그인**: `master` 계정과 비밀번호로 승인된 일반 로그인 API를 호출. HTTP 상태, 요청 Content-Type, 응답 인증 데이터 형식 확인. 비밀번호·토큰은 기본 로그 마스킹.
- [ ] **R-03 인증 전달**: 로그인 후 저장된 토큰 또는 쿠키를 다음 요청에 올바르게 부착하는지 확인. `Authorization: Bearer ...`를 무조건 가정하지 않음. 인증 정보는 메모리에서만 유지.
- [ ] **R-04 단건 조회**: `POST /api/wpf/popups` 요청 본문 `{}` → `pollingIntervalSeconds` 및 `popup` 확인. `popup=null`은 정상 결과로 처리.
- [ ] **R-05 실제 렌더링**: 반환된 팝업의 `deliveryId`, `popupId`, 콘텐츠 유형과 실제 화면을 비교. TEXT/IMAGE/VIDEO/SURVEY/QUIZ, VIDEO+QUIZ는 테스트 데이터가 준비된 유형만 순차 수행.
- [ ] **R-06 결과 제출**: 실제 팝업 닫기/제출 시 `POST /api/wpf/popups/results`로 `resultId`·`deliveryId`·`popupId`·`resultType` 전송, 서버의 `status`·`nextStatus` 확인.
- [ ] **R-07 다음 조회**: `AVAILABLE`이어도 자동 호출하지 않고 버튼으로 수동 조회. `EMPTY`·미전송 결과 존재 시 현재 정책 유지.
- [ ] **R-08 오류/복구**: 잘못된 비밀번호, 미인증·401, 로그인 응답에 토큰 없음/응답 형태 불일치(토큰 기반일 때), 403·404·426·500, 잘못된 JSON, 타임아웃·연결 실패, 중복 클릭을 구분해 표시.
- [ ] **R-09 재전송/멱등**: 로그인 이후 401 시 승인된 재인증 방식으로 최대 1회 재시도. 결과 재전송 시 동일 `resultId` 및 동일 본문 유지; `DUPLICATE` 처리 확인.
- [ ] **R-10 기존 모드 보호**: 인메모리 Demo, 기존 SSO 프로토타입 모드, 직접 토큰 입력 모드, 일반 실행 자동 폴링이 영향을 받지 않는지 확인.
- [ ] **R-11 증적**: 요청/응답 구조와 HTTP 상태, 소요 시간, 토큰 마스킹된 로그, 팝업 표시/닫힘, 최종 성공·실패·미실행 항목 기록. 실제 개발/검증 DB 데이터 변경은 테스트 범위에 포함되므로 대상 계정/환경 확인.
