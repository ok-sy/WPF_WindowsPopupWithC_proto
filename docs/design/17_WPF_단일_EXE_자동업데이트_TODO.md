## 1. 목적과 현재 상태

MSI 설치 패키지 없이, self-contained 단일 EXE를 다운로드한 뒤 기존 EXE와 교체하는 방식으로 업데이트한다. PowerShell 스크립트가 앱 종료 대기·백업·교체·재실행·실패 복구를 담당하는 구성을 우선 검토한다. 별도 상주 업데이트 서비스는 초기 범위에 넣지 않는다.

현재 `Popup.exe`는 win-x64용 .NET 런타임 포함 단일 EXE로 게시할 수 있다. 2026-09-23 배포본은 85,666,721바이트(약 81.7MiB)다. .NET 런타임도 새 EXE에 포함되지만 WebView2 Runtime 등 별도 외부 구성요소의 설치·갱신까지 해결하는 것은 아니다.

현행 구현은 `ClientVersion`의 실행 버전, 요청의 `X-Client-Version`, 서버의 최소 지원 버전 검사, HTTP 426 안내·조회 중단·미전송 결과 보존까지다. 자동 다운로드, 그룹 배정, 교체 스크립트, 기동 확인, 복구는 아직 구현되지 않았다. 기존 수동 배포 경로는 `D:/work/PopupProject2026/dist/Popup.exe`다.

## 2. 버전 3단계와 기본 배포 정책

버전은 `MAJOR.MINOR.PATCH` 세 숫자로 관리한다. 각 숫자는 변경 규모를 나타내며, 이를 기본 배포 정책 선택에 활용한다. 비교는 문자열 순서가 아니라 숫자 세 부분으로 한다. 같은 버전 번호로 다른 EXE를 재게시하지 않는다.

| 단계 | 변경 예 | 기본 배포 정책(초안) |
|---|---|---|
| 1lv / MAJOR | 1.0.0 → 2.0.0 | 긴급 배포: 대기 시간 최소화, 짧은 그룹 간격 적용 |
| 2lv / MINOR | 1.0.0 → 1.1.0 | 유휴 시간에 그룹별 순차 배포 |
| 3lv / PATCH | 1.0.0 → 1.0.1 | 더 여유 있는 일정으로 그룹별 순차 배포 |

개선: 버전 단계와 실제 긴급도는 분리한다. 서버가 릴리스마다 `urgency: NORMAL | URGENT`를 명시하고 최종 일정에 반영한다. MAJOR는 기본 URGENT로 제안하되 NORMAL로 조정할 수 있고, 심각한 오류를 고치는 PATCH도 URGENT로 지정할 수 있다. 여러 단계가 한꺼번에 달라지면 가장 높은 변경 단계를 기본값에 사용한다.

`urgent`와 `mandatory`도 구분한다. 전자는 배포 속도, 후자는 설치 기한과 지원 정책이다. 긴급 배포라도 모든 PC의 즉시 동시 다운로드나 작성 중인 설문·퀴즈의 강제 종료를 기본 동작으로 삼지 않는다. 기한 초과 때 새 팝업을 막고 현재 작업 완료를 기다릴지 등 세부 정책은 구현 착수 전에 확정한다.

단순히 버전이 다르다는 이유로 교체하지 않는다. 서버가 이 PC에 지정한 목표 버전이 더 높고 배포가 활성화된 경우에 진행한다. 동일 버전은 아무 작업도 하지 않으며, 낮은 버전으로의 교체는 명시적 복구 정책에만 허용한다. `latestVersion`은 전체 최신 버전, `targetVersion`은 현재 PC의 배포 목표로 구분한다.

## 3. 서버와 클라이언트의 역할

| 구성요소 | 역할 |
|---|---|
| 서버 | 릴리스 메타데이터, 목표 버전, 긴급도, 배포 그룹, 허용 시각·설치 기한, 중단·재개 정책 관리 |
| 파일 제공 경로 | 버전별 변경되지 않는 EXE 제공. 사내 HTTP 파일 서버 등 기존 정적 파일 제공 경로 활용 검토 |
| WPF | 버전·설치 식별자 전달, 일정 보존, 백그라운드 다운로드·검증, 안전한 교체 시점 판단, 결과 보고 |
| PowerShell | 지정된 앱 종료 확인, 이전 파일 백업, 검증된 새 EXE 교체, 재실행, 기동 확인 및 복구 |

최초 실행 및 제한된 주기의 통신에서 업데이트 정보를 확인한다. 기존 목록 조회 응답에 메타데이터를 포함할지, 별도 업데이트 조회 API를 둘지는 착수 시 확정한다. 버전 검사 실패로 기존 로그인·조회가 막힌 PC도 업데이트 정보를 받을 수 있어야 한다. 업데이트 전용 경로의 인증 방식을 별도로 설계하되 기존 업무 API 인증을 우회하는 방식은 사용하지 않는다.

### API 계약 후보 (미구현)

실제 URL·DTO·DB 컬럼을 확정한 계약이 아니라 이후 구현 시 검토할 항목이다.

| 방향 | 필드 후보 | 의미 |
|---|---|---|
| 요청 | currentVersion, installationId, platform | 현재 실행 버전, 설치 단위의 영속 식별자, win-x64 등 대상 플랫폼 |
| 응답 | releaseId, targetVersion, minimumSupportedVersion | 릴리스 식별, 해당 PC 목표, 업무 API 최소 지원 버전 |
| 응답 | urgency, mandatory, rolloutState | 긴급도, 의무 적용 여부, ACTIVE/PAUSED/CANCELLED |
| 응답 | groupId, serverTime, downloadNotBefore, installDeadline, nextCheckAt | 그룹, 서버 시간, 다운로드 허용 시각, 설치 기한, 다음 확인 시각 |
| 응답 | downloadUrl, sizeBytes, sha256, signatureMetadata | 배포 파일 경로·크기·검증 정보 |
| 결과 | releaseId, currentVersion, state, errorCode | 대기·다운로드·준비·교체·완료·복구·실패 등 상태 보고 |

시간은 UTC의 오프셋 포함 형식으로 전달하고 화면·기록에서 KST로 표시한다. 단말 시계 차이는 serverTime을 기준으로 보정한다. URL 유효기간은 예약 시각과 다운로드 시간을 포함해야 하며, 만료되면 메타데이터를 다시 받아 갱신한다. 상태 보고에는 토큰 등 인증 정보를 기록하지 않는다.

## 4. 그룹별 시간 분배와 트래픽 제어

예시: 1,000대를 100대씩 10개 그룹으로 나누고 5분 간격으로 다운로드 시작을 허용한다. 그룹 내부에도 랜덤 지연을 둬 같은 초에 접속하지 않게 한다. 수치와 간격은 예시이며 대수·망 대역폭·영상 이용량 측정 후 결정한다.

- 설치 시 생성하여 보관한 식별자를 사용한다. 공유 PC·다중 사용자 실행이 가능하면 PC 단위와 사용자 단위 중 어느 범위로 설치·잠금을 관리할지 먼저 확정한다.
- `releaseId + installationId`의 안정적인 해시로 그룹 후보를 만들거나 서버가 할당한다. 해시는 근사 분배이며 정확한 그룹별 인원 제한은 서버 할당이 필요하다.
- 같은 릴리스의 배정 결과는 재시작·재로그인 후에도 유지한다. 설정 변경으로 전체 PC가 새 그룹으로 즉시 이동하지 않도록 한다.
- 오프라인 PC가 예약 시각을 놓쳤다고 접속 즉시 전부 다운로드하지 않는다. 재접속 시 서버가 남은 용량에 맞춰 재배정한다.
- 시작 시각 분산만으로 최대 동시 다운로드 수가 보장되지는 않는다. 전송이 느리면 앞 그룹이 다음 그룹과 겹치므로 동시 허용 수·전송률 제한도 검토한다.
- 실패 재시도는 횟수 제한과 지수 지연·랜덤 지연을 둔다. 서버가 지정한 다음 확인 시각을 존중한다.
- 긴급 배포는 간격을 줄여 우선 처리하되 최소한의 동시성 제한을 유지한다.
- 소수 PC 선행 배포 → 정상 기동 확인 → 다음 그룹 확대를 권장한다. 오류가 늘면 서버에서 새 다운로드·설치를 중단한다.

리소스는 영상 스트리밍과 마찬가지로 네트워크 대역폭이 주요 검토 항목이지만, 업데이트는 유한한 파일을 한 번 받는 작업이다. 현재 파일 크기로 1,000대가 한 번씩 받으면 약 85.7GB(10진수)이고, 10분 안에 모두 받으면 이론상 평균 약 1.14Gbps가 필요하다. 프로토콜 비용·재시도·기존 영상 트래픽은 별도다. 그룹 분산은 총 전송량을 줄이지 않고 순간 부하를 낮춘다. 최초 구현은 전체 EXE 다운로드로 하고 차등 업데이트는 필요성이 확인된 후 별도 후순위로 검토한다.

## 5. 다운로드와 EXE 교체 절차

1. 앱은 서버의 목표 버전·일정·배포 상태를 확인하고 releaseId별 상태를 저장한다.
2. 허용 시각이 되면 새 EXE를 임시 파일로 다운로드한다. 실행 파일 경로에 직접 다운로드하지 않는다.
3. 파일 크기·SHA256·대상 플랫폼·버전을 확인한다. 신뢰된 HTTPS 경로와 서명 검증 방식을 함께 설계한다. 동일한 비신뢰 경로에서 받은 해시만 비교하는 것으로 배포 출처까지 검증했다고 보지 않는다.
4. 다운로드와 설치 시점을 분리한다. 다운로드가 끝나도 팝업·영상·설문이 진행 중이면 교체를 대기한다. 여기서 유휴는 우선 앱의 진행 중 작업이 없는 상태를 뜻하며, PC 전체 입력 유휴 시간 조건은 선택 사항으로 둔다.
5. 설치 직전에 서버의 배포 중단 여부와 파일 검증 결과를 다시 확인한다. 새 팝업 생성을 막고 결과 큐를 디스크에 보존한다. 서버 전송 성공을 기다리지 못하더라도 저장된 결과는 유지한다.
6. 앱이 별도 PowerShell 프로세스에 검증된 경로·기존 PID와 시작 시각·releaseId를 전달하고 정상 종료한다. 스크립트는 눈에 보이는 콘솔 없이 실행하는 구성을 검토한다.
7. 스크립트는 지정 앱의 실제 종료와 파일 잠금 해제를 제한 시간 동안 기다린다. 프로세스 이름 전체를 일괄 종료하지 않으며, 무조건적인 강제 종료를 기본값으로 두지 않는다.
8. 기존 EXE를 백업하고 새 EXE로 교체한다. 가능한 동일 볼륨에서 교체하고 중간 상태를 기록해 전원 종료 후 복구할 수 있게 한다.
9. 동일한 사용자 세션·작업 디렉터리·허용된 실행 인자로 재실행한다. 새 프로세스가 떴다는 사실만으로 성공 처리하지 않는다.
10. 새 앱은 지정 releaseId의 로컬 기동 완료 신호를 남긴다. 필수 초기화와 로컬 큐 읽기 성공을 확인하고 서버 연결 성공 여부는 별도 상태로 취급한다. 네트워크 단절만으로 불필요한 복구를 반복하지 않는다.
11. 제한 시간 내 기동 확인 실패 또는 반복 크래시이면 이전 EXE를 복원하고 재실행한다. 실패한 릴리스를 기록하여 동일 버전 설치·복구가 무한 반복되지 않게 한다.
12. 성공·실패·복구 결과는 연결 가능한 시점에 서버에 보고한다. 백업은 성공 확인과 보존 기간이 지난 뒤 정리한다.

## 6. 현행 구조와의 정합성 보완

- **기존 426 차단과 순차 배포:** 전체 minimumSupportedVersion을 먼저 높이면 아직 배포 순서가 오지 않은 PC도 차단된다. 정상 순차 배포에서는 구버전 호환 기간을 유지하고 충분한 배포 확인 후 최소 버전을 올린다. 즉시 차단이 필요한 릴리스는 업데이트 경로 접근성과 사용 중단 정책을 먼저 확보한다.
- **기존 CrashGuard·단일 인스턴스:** 계획된 업데이트 종료·복구 중 자동 재시작이 파일 교체와 경쟁하지 않도록 업데이트 상태를 공유한다. 스크립트와 새 앱 사이에 잠금·기동 확인을 두고, 다중 세션에서 같은 EXE를 사용하는 경우도 다룬다.
- **미전송 결과·설정 보존:** pending 결과, 식별자, 환경별 설정, 로그를 교체 대상으로 포함하지 않는다. 외부 파일뿐 아니라 EXE에 포함된 appsettings의 환경 값도 릴리스 생성 시 확인한다. 구버전으로 복구해도 큐를 읽을 수 있도록 데이터 변경은 호환성을 유지한다.
- **설치 경로와 권한:** 앱과 스크립트에 설치 폴더 쓰기 권한이 있는지 사전에 확인한다. 권한이 없으면 앱 종료 전에 안내·보류한다. Program Files 등 보호 경로는 별도 권한 설계가 필요하며 일반 사용자 실행을 전제로 조용한 관리자 승격을 가정하지 않는다.
- **PowerShell 실행 정책:** 폐쇄망 PC의 스크립트 실행·서명 정책에 맞는 방식으로 준비한다. 정책 강제 우회를 전제로 만들지 않는다. 최초 배포에는 스크립트 실행을 시작할 수 있는 클라이언트 기능이 포함되어 있어야 한다.
- **실패 중단·되돌리기:** 내려받은 후 배포가 취소되면 교체하지 않는다. 이미 성공적으로 설치된 PC의 다운그레이드는 별도 정책이며 API·큐 포맷 호환성을 확인한다. 긴급 변경으로 구버전 사용이 금지된 경우 파일 복구 가능 여부와 업무 API 허용 여부를 구분한다.

## 9. 완료 기준 — 아직 미검증

- 동일 버전·서버보다 높은 버전·잘못된 버전에는 무의미한 교체가 발생하지 않는다.
- MAJOR 기본 긴급, MINOR/PATCH 순차 배포 및 PATCH 긴급 지정이 정책대로 동작한다.
- 재시작·오프라인 복귀·그룹 일정 경과·서버 시간 차이에서도 다운로드가 한 시점에 몰리지 않는다.
- 손상 파일·서명 불일치·다운로드 중단·디스크 부족·쓰기 권한 없음·파일 잠금에서 기존 EXE와 큐가 보존된다.
- 팝업·영상·설문 진행 중 설치를 연기하고 종료 후 안전하게 교체한다.
- 정상 업데이트 후 새 버전 기동 확인과 상태 보고가 이뤄지고, 실패 시 제한된 횟수로 복구한다.
- 교체 중 강제 전원 종료·재부팅·CrashGuard 자동 재시작·동시 업데이트 시도에서 중복 실행과 파일 유실이 없다.
- 구버전 차단 상태에서도 업데이트를 받을 수 있고 그룹 대기와 API 최소 버전 정책이 충돌하지 않는다.
- 실제 폐쇄망 PC에서 MSI와 별도 .NET 설치 없이 단일 EXE 교체가 동작한다. 외부 구성요소는 별도로 확인한다.
- 문서에 정한 동시성·대역폭·재시도 상한과 배포 중단 동작을 부하 시험으로 확인한다.
